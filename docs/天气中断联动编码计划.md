# 天气 → 航班中断 → 三页联动编码计划（优化版）

> 状态：计划中（待确认后实施）
> 本版基于"回滚全部编码"后的当前代码，重点解决：**复用后端已有天气异常算法** + **前端天气/模拟引擎/旅客流三页一致**。

---

## 0. 一句话说清这次要做什么

> 天气模拟页已经有一套**随气旋动画实时更新的各省天气表**（气旋推到广东，广东就自动变成雨天）。前端**实时把这张表自动回传后端**，并用**气旋确定性推演**预演出"每个省未来几点开始下雨、几点停" → 后端**复用已有的异常调度算法**自动算出"哪些航班延误/取消" → **模拟引擎**自动调整航班飞行效果（取消=红弧、延误=橙弧、延后/不起飞） + **旅客流**自动调整飞机起降与粒子进出站效果（取消灰显不生成粒子、延误延后登机/起降）。全程**无需手动发布、无需手动估时间**。

关键诉求只有两个词：**复用** + **一致**。

- **复用**：`city_geo`（起降点+途经省份判定）和 `impact_analysis_service`（GDP 延迟 + BFS 级联 + 5h 取消）早已写好，本次**零改动调用**，新代码只做"气象源 → 装配 AbnormalEvent → 调用 analyze → 产出中断计划"这段桥接。
- **一致**：指**数据同步一致，而不是三页同时渲染**。同一时间只能切到一个页面看，但三个页面共享**同一份 `disruption_plan`**——切到任何一页，看到的都是同一时刻、同一份计划推导出的结果，同一架航班不会出现"引擎页延误、旅客流页却正常起飞"。

---

## 1. 三条核心原则

1. **复用已有算法，不重写调度逻辑**：省份级受影响航班判定、延迟/取消计算全部走既有 `city_geo` + `impact_analysis_service`，本次不新写任何"简化的 Slot 挤出 / 整省全停"逻辑。
2. **一份中断计划，三页共享（一致性）**：后端 `state` 里只存一份 `disruption_plan`，模拟引擎和旅客流两个消费端都从它读，保证三页结果一致。
3. **分立渲染，状态串通**：三页面各自独立渲染（合一起会卡死），同一时间只切到一个页面看；但都从后端同一份共享状态轮询，**切换页面后数据自动对齐、保持同步一致**，不上 WebSocket。

## 4. 天气类型映射（前端 6 类 ↔ 后端容量）

前端 `weatherTypes` 6 类：`sunny / cloudy / rain_light / rain_moderate / rain_heavy / thunderstorm`。

统一在**后端**新增映射表（不侵入前端 3D 渲染）：

```python
# backend/services/weather_disruption_service.py
FRONT_WEATHER_MAP = {
    'sunny':          {'capacity': 1.0, 'severity': 0, 'disrupted': False},
    'cloudy':         {'capacity': 0.9, 'severity': 0, 'disrupted': False},
    'rain_light':     {'capacity': 0.8, 'severity': 1, 'disrupted': True},
    'rain_moderate':  {'capacity': 0.7, 'severity': 2, 'disrupted': True},
    'rain_heavy':     {'capacity': 0.5, 'severity': 3, 'disrupted': True},
    'thunderstorm':   {'capacity': 0.4, 'severity': 4, 'disrupted': True},
}
```

- `sunny/cloudy` 不触发中断。
- `rain_light` 及以上为"坏天气"，**只降容量、不停运**（符合"非暴力"）。
- `severity` 用于异常优先级与容量分级；持续时间由气旋推演时间线提供（见第 5 节）。

## 5. 核心难点：如何判断"异常天气持续多久"

真实航司做法 = **气象预报 + 容量模型 + GDP + 恢复爬坡**，而不是"某省下雨 N 小时 → 全停 N 小时"。

`impact_analysis_service.analyze()` 要的 `start_time/end_time`，本质是"坏天气在**业务时钟**上的起止"。本方案**不用手动估窗口**，直接用气旋确定性推演得到。

### 5.1 影响时间来源：气旋确定性推演（唯一主方案）

关键点：气旋是**确定性系统**，不是随机播放。`WeatherMap3D` 里：

- `cy.phase += dt / CYCLONE_CYCLE`，phase 随时间**线性**推进（`CYCLONE_CYCLE` 见 5.3 统一时钟，已放慢）；
- 位置 = `interpolateAlongPath(CYCLONE_PATHS[pathKey], phase)`；
- 强度 = `calcCycloneIntensity(phase, efPeak)`。

所以"某省未来几点开始下雨、几点停"可以**直接快进算出来**，不用等动画播到那一刻，也不用人工设窗口。

前端新增 `predictProvinceTimeline(durationMinutes)`：从当前各气旋 phase 出发，用**同一个 `getWeatherAt`** 逐时间步外推各省天气，得到 `{省: [{t, type}...]}`；后端从中提取每省"连续坏天气的 [start, end]"，直接填 `AbnormalEvent.start_time/end_time`。

### 5.2 稳态模式兜底（auto / manual）

auto/manual 是稳态天气，无气旋可推演、无"自然转好"时刻。此时 timeline 为空，后端**自动**按 severity 给一个持续窗口（非手动）：

```python
SEVERITY_WINDOW_MIN = {1: 90, 2: 150, 3: 210, 4: 150}
# 小雨/中雨/大雨/雷暴；雷暴短而强，大雨持续更久
```

恢复走**爬坡**而非瞬切：`capacity 恢复序列 = [0.2, 0.4, 0.7, 1.0]`，每 30min 升一档。

### 5.3 业务时间锚点（三模块统一时钟）

三个页面各有一个演示时钟，速率差异导致"天气跑太快、引擎/旅客流跟不上"：

| 模块 | 原速率（业务分钟/秒） |
|------|---------------------|
| 天气动画 | ~168（60s 播完 7 天） |
| 模拟引擎 | ~5（默认倍速 1） |
| 旅客流 | ~1（默认倍速 1） |

统一方案（已确认）：**放慢天气动画 + 以天气 phase 映射为统一时间锚点**：

- 天气动画速率从 168 降到 **5 业务分钟/秒**（对齐模拟引擎默认倍速），即一个完整气旋周期由 60s 改为 `7×24×60 ÷ 5 = 2016s`。
- 定义气旋 **phase 0 ↔ 2020-11-29 00:00**（生成数据首日），phase 线性映射为绝对业务分钟 `40320 + phase × 10080`（后端分钟自 2020-11-01 00:00 起算，与 `SimulationEngine._time_to_min` 一致）。
- 前端 `predictProvinceTimeline` 预演时，每个采样点同时输出 `t`（相对分钟）与 `time`（绝对业务时刻 "YYYY-MM-DD HH:MM"），后端直接以 `time` 作为坏天气 `[start, end]`，无需再估时间。
- 三页共享同一业务时间轴：天气页 phase 映射出的时刻，就是模拟引擎/旅客流此刻应处的业务时刻；切页后数据对齐。

## 6. 已有算法如何被复用（后端桥接核心）

`weather_disruption_service.compute_disruption()` 是本次**唯一的后端新逻辑**，但它本身不含调度算法，只是把已有函数按顺序串起来：

```python
def compute_disruption(province_weather, timeline, flights, aircraft_map, chains, transit_cache) -> dict:
    # 1) 前端天气类型 → 坏天气省份
    bad_provinces = {p for p, t in province_weather.items()
                     if FRONT_WEATHER_MAP.get(t, {}).get('disrupted')}

    # 2) 复用：坏省份 → 机场列表
    airports = get_province_airports(bad_provinces)

    # 3) 复用：受影响航班（起降点在该省 = direct；途经该省 = transit）
    affected = get_affected_flights_by_province(flights, bad_provinces, transit_cache)
    direct_ids, transit_ids = affected['direct'], affected['transit']

    # 4) 影响时间：气旋推演 timeline 提取每省坏天气 [start,end]；无 timeline 则 severity 兜底
    windows = extract_windows_from_timeline(timeline, bad_provinces)   # {省: (start_str, end_str)}
    start_str, end_str = merge_windows(windows)                        # 多省取最早开始/最晚结束

    # 5) 复用：构造 AbnormalEvent + schedule，调 impact_analysis_service
    #    direct 航班走 GDP 延迟 + BFS 级联 + 5h 取消
    event = AbnormalEvent(
        event_id=f"weather_{int(time.time())}",
        event_type=AnomalyType.WEATHER_CAPACITY,
        title=f"省份天气中断: {'、'.join(bad_provinces)}",
        affected_airports=airports,
        start_time=start_str, end_time=end_str,
        capacity_ratio=min_capacity,
        severity=max_severity,
    )
    report = impact_analysis_service.analyze(event, {
        'flights': flights,
        'aircraft_assignments': aircraft_map,   # flight_id -> tail_no（已有缓存）
        'crew_assignments': {},                 # 可空
        'gate_assignments': {},                 # 可空
        'runway_assignments': {},               # 可空
        'chains': chains,                       # list[list[Flight]]（已有缓存）
    })
    # report.timeline_changes: {flight_id: {delay_minutes, reason, level}}
    # report.flights_to_cancel: [flight_id]  (delay >= 5h)

    # 5) transit 航班：绕飞延迟 +30~60min，不取消（复用 city_geo transit 结果）
    # 6) 合并 → 统一的中断计划
    plan = {}
    for fid, tc in report.timeline_changes.items():
        is_cancel = fid in report.flights_to_cancel
        plan[fid] = {
            'type': 'cancel' if is_cancel else 'delay',
            'delay_minutes': tc['delay_minutes'],
            'reason': tc['reason'],
            'affected_by': 'direct',
            'airport': None,
        }
    for fid in transit_ids:
        if fid in plan:  # direct 优先，避免覆盖
            continue
        plan[fid] = {
            'type': 'delay',
            'delay_minutes': 30 + ...,
            'reason': '途经天气省份绕飞',
            'affected_by': 'transit',
            'airport': None,
        }
    return plan
```

**数据来源（均已存在，无需新建）**：
- `flights`：`state.get_active_flights()` 或 `state.get_generated_data()['flights']`
- `aircraft_map`：`schedule_routes._get_flight_aircraft_map()`（flight_id → tail_no）
- `chains`：`schedule_routes._get_aircraft_routing()`（list[list[Flight]]）
- `transit_cache`：`state.get_transit_cache()`（已由 `_rebuild_transit_cache` 构建）

## 8. 三页一致性的具体表现（验收对照表）

> 同一份 `disruption_plan`，同一 `flight_id`，三页看到的结果必须一致。以下以"广东设为雷暴"为例：

| 现象 | 天气模拟页 | 模拟引擎页（FlightMap3D） | 旅客流页（FlightBoard + TerminalLayout） |
|------|-----------|--------------------------|----------------------------------------|
| 受影响范围 | 自动回传后实时回显：广东相关机场、direct/transit 数 | 状态栏"延误 X / 取消 X" | 航班动态出现取消/延误标签 |
| 取消航班 | — | 红色航线弧，无飞机模型 | 灰显 + 删除线，不生成乘客粒子/不 preload 飞机 |
| 延误航班 | — | 橙色航线弧，飞机延后起飞/停地面 | 橙色 + `延误 XX min`，粒子延后登机、飞机延后起降 |
| 不受影响航班 | — | 正常起降 | 正常起降 + 粒子正常进出站 |

**一致性断言**：对任意 `flight_id`，其 `type/delay_minutes/reason` 在引擎快照和 `paxflow/schedule?disrupted=true` 中必须相等。

## 11. 不做什么（边界）

- **不做"省份下雨→全省停运"**：只用容量比 + GDP + 5h 阈值，保留部分运行能力。
- **不重写调度算法**：`city_geo` / `impact_analysis_service` 一行不改，只调用。
- **不做 WebSocket 推送同步**：天气自动回传用前端节流轮询（每 2s POST），三页面各自 poll 后端共享状态，符合"分立渲染、状态串通"。
- **不改前端 3D 天气渲染内核**：只新增"读表 + 气旋预演"入口，不侵入气旋/雨粒子算法。
- **不把自动天气事件强写进异常面板数据库**：plan 存内存共享状态即可，后续可再落库。
- **不新增旅客流页面路由**：继续用既有 `/api/paxflow/schedule`，只加查询参数与返回字段。
