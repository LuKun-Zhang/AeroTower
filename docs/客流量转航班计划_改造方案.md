# 客流量 → 航班计划 全链路打通改造方案

> 目标：用户只需上传/输入各城市客流量数据，系统自动生成**带旅客明细（精确到座位号）**的航班计划，直接进入跑道/登机口/机组调度与旅客流仿真，无需人工筛选原始航班。
>
> **机型**：本项目固定使用 A319（C8Y124，132 座：8 公务 + 124 经济）。

---

## 一、新旧链路对比

```
【旧链路：半自动，依赖真实航班数据】
  上传 xlsx 航班计划 → filter_flights（DFS搜索任务链，成功率不确定）
  → 人工确认闭环航班 → 跑道/登机口/机组调度 → 旅客流仿真（粒子随机生成）

【新链路：全自动 + 旅客级精确】
  输入城市客流量（精确到人，每人有唯一编号）→ 航班生成器
  → 生成航班 + 任务链 + 座位分配（Pax-00001 → 3U8001 → 12A）
  → 跑道/登机口/机组调度（不变）→ 旅客流仿真（真实编号粒子，可追溯到座位）
```

| 维度 | 旧链路 | 新链路 |
|------|--------|--------|
| 输入 | 航班计划 xlsx | 城市客流量数据 |
| 旅客粒度 | 粒子随机生成，无编号 | 每人唯一编号，精确到座位 |
| 可追溯性 | 无法追溯旅客 | Pax-00001 → 3U8001 → 12A → 登机口 |
| 任务链 | DFS 搜索，可能不满 | 生成时即保证，100% |
| 人工介入 | 需要确认筛选结果 | 完全自动 |
| 下游模块 | 跑道/登机口/机组/仿真 | **零改动复用** |

## 1.5 A319（C8Y124）座位布局

本项目固定使用 A319 机型，客舱布局 **C8Y124 = 132 座**。

```
座位编号规则：
┌─────────────────────────────────────────────┐
│  公务舱（C8）：第 1-2 排                      │
│  编号：1A 1C 1D 1F / 2A 2C 2D 2F           │
│─────────────────────────────────────────────│
│  经济舱（Y124）：第 3-33 排                    │
│  编号：排号 + A/B/C/D/E/F（共 6 列）          │
│  3A 3B 3C 3D 3E 3F                          │
│  4A 4B 4C 4D 4E 4F                          │
│  ...                                         │
│  33A 33B 33C 33D 33E 33F                     │
│─────────────────────────────────────────────│
│  总计：8（公务）+ 124（经济）= 132 座          │
└─────────────────────────────────────────────┘
```

**旅客 ID 格式**：`Pax-{日期}-{序号}`，如 `Pax-1130-00001` 表示 11 月 30 日第 1 位旅客。

## 三、后端改造

### 3.1 新模块：`backend/services/flight_generator.py`

**核心类**：`FlightGenerator`

**输入数据结构** (`TrafficData`)：

```python
{
    "hub": "成都",                    # 枢纽机场（基地）
    "dates": ["2020-11-30", ..., "2020-12-05"],  # 日期范围
    "ac_type": "A319",               # 机型
    "layout": "C8Y124",              # 客舱布局
    "seat_capacity": 132,            # 座位数
    "load_factor": 0.78,             # 客座率
    "min_turnaround": 60,            # 最小过站时间（分钟）
    "max_segments_per_day": 5,       # 单日最大段数
    "max_daily_flight_hours": 8,     # 单日最大飞行小时
    "city_traffic": [                # 各城市客流量
        {
            "city": "北京",
            "daily_pax": 1200,        # 日客流量（人次）
            "inbound_ratio": 0.45,    # 进港方向占比
            "flight_duration": 150,   # 飞行时长（分钟，可选，默认查距离表）
        },
        {
            "city": "上海",
            "daily_pax": 1000,
            "inbound_ratio": 0.50,
            "flight_duration": 160,
        },
        ...
    ]
}
```

**核心算法流程**：

```
1. 生成旅客池（Passenger Pool）
   遍历 city_traffic，为每个城市 × 每天生成 daily_pax 个旅客
   每个旅客：唯一 ID（Pax-MMDD-NNNNN）、出发城市、目的城市（成都）
   进港旅客：city → 成都，出港旅客：成都 → city

2. 计算各城市所需航班数
   日进港航班 = ceil(daily_pax × inbound_ratio / (capacity × load_factor))
   日出港航班 = ceil(daily_pax × (1-inbound_ratio) / (capacity × load_factor))

3. 座位分配（Seat Assignment）
   为每个航班遍历旅客池取对应目的地旅客，按顺序分配座位
   公务舱（1A-2F，共 8 座）优先分配（若客座率 > 90% 才启用）
   经济舱（3A-33F，共 124 座）按排×列顺序填充
   座位满则增加航班
   每位旅客记录：pax_id → flight_no → seat_no

4. 构建往返航班对（Round-Trip Pair）
   成都→北京（departure） + 北京→成都（arrival）= 一对
   保证每对在时间上可衔接（过站 ≥ 60min）
   去程的到达旅客 + 回程的出发旅客 = 各自独立的旅客池

5. 生成每日航班模板（Daily Template）
   以给定的日期范围，为每个城市生成每日固定的往返航班对
   举例：成都→北京 08:00-10:30（132座，103人），北京→成都 11:30-14:00（132座，97人）

6. 组合成多日任务链（Chain Assembly）
   将同机型、可衔接的每日模板按日串联
   链首尾均在枢纽（成都）
   约束：单日 ≤ 5 段，日飞行 ≤ 8h，跨天休息 ≥ 10h

7. 构造 Flight 对象 + 旅客清单（Passenger Manifest）
   为链中每个航段创建 Flight 对象，字段与现有 Flight 模型完全一致
   每个 Flight 附带 passenger_manifest：座位号 → 旅客 ID 的完整映射
   分配航班号：3U8xxx 格式，链内依序编号
```

**输出结构**：

```python
{
    "flights": [
        {
            "flight_id": "gen_001",
            "flight_no": "3U8001",
            "ac_type": "A319",
            "departure_airport": "成都",
            "arrival_airport": "北京",
            "time_departure": [2020, 11, 30, 8, 0],
            "time_arrival": [2020, 11, 30, 10, 30],

            "passenger_manifest": {       # ← 新增：旅客清单
                "1A": None,              # 公务舱空座
```

## 六、关键设计决策

1. **生成 vs 筛选**：新模块不依赖 `big.json` 原始航班数据，完全从客流量凭空生成。旧 `filter_flights` 链路保留作为兼容入口。

2. **链的天然性**：生成算法保证每条链首尾均在枢纽（成都），相邻航段时空衔接。不需要事后验证闭环。

3. **旅客生成时机**：在航班生成之前先生成旅客池（每人有唯一 ID），再按目的地将旅客分配到具体航班的座位上。保证每个旅客都可追溯到航班号和座位号。

4. **座位分配策略**：按经济舱优先（3A→3B→3C→...→33F），公务舱仅在客座率 > 90% 时启用。座位满则自动增加航班。

5. **飞机排班**：生成的链直接就是飞机任务，可跳过 `solve_chain_coverage`。保守做法：仍走一遍路由，但路由会直接接受完整链（无重叠问题）。

6. **多天连续**：同一城市的往返航班对在每一天固定时刻，链跨越日期时自动衔接前一天的最后一班和当天的第一班。

7. **数据持久化**：生成结果同时存入 `state` 模块（运行时）和可选导出到 `_days_data.json`（持久化，供旅客流仿真用）。旅客索引额外存入 `passenger_index.json` 供快速查询。

8. **单一机型**：本项目固定 A319（C8Y124），座位号格式固定（1A-2F 公务 + 3A-33F 经济）。后续支持多机型时只需扩展座位号生成器。
