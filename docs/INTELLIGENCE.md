# 第二步智能化改造：使用与验收

更新：2026-11-27。项目基线 `6ef014a8582e3ec158cee3abfbb7176d66267ed8`，本地分支 `codex/intelligence-phase2`。

本项目是可在普通电脑上运行的教学实验原型。新增模型负责预测和辅助选择，原调度器计算、确认和执行方案。所有“实际延误”均指系统模拟结果；真实公开数据的检查单独列出。

## 1. 六项补齐内容

| 原欠缺 | 已实现的行为 | 验收方式 |
| --- | --- | --- |
| 客流趋势预测 | 实验前查看趋势、同期对照和预测客流；可把日客流比例与天数填入条件草稿 | 连续时间尾部留出，与上周/上年同期值比较；验证递归预测不读取未来真实值；浏览器查看曲线并填表 |
| 排班算法推荐 | 比较原链覆盖、贪心、车辆路径算法，显示计划代价与约束；选用只改变原页面算法下拉框 | 80个主留出、两组各40个附加场景；实际点击原“一键排班”，核对请求的算法与返回结果 |
| 预测命中率 | 模型评估及实验结果显示命中百分比；单次结果同时列出判断正确架数/总架数 | 以概率≥50%判为延误，与模拟延误超过15分钟的标签逐架核对 |
| 原恢复流程对照 | 同一份航班和异常，真正调用原 RecoveryService 生成、确认、执行副本并统一计分 | 原页面生成的计划与隔离对照成本一致；实际确认、执行原恢复流程成功 |
| 失准复核与回退 | 运行时每7天检查固定模型；失败停用对应预测/建议，正常复核通过后恢复 | 人为扰动的演示复核使延误模型停用，页面与接口回退；正常复核恢复，模型权重哈希不变 |
| 本地语言解析 | 官方1.5B本机CPU提取，最多一次只给字段名的纠错后合并；失败明确回退模板 | 8开发+16旧回归+24新留出；首轮29/48，两轮合并48/48，新留出24/24；每个模型值来源审计通过 |

同一批旧24条，原流程一次反馈后16/24正确，新流程两轮模型提取合并后24/24；另24条未参与调试的新描述也24/24。整体48条达到原先设定的90%启用线，默认启用本地模型流程。首轮单次提取只有29/48（60.42%），不能写成“一次输出100%正确”或“任意说法都能理解”。完整记录见 `data/intelligence/language-evaluation.json`，独立来源核对见 `.artifacts/verification/language-provenance-audit.json`；模板补漏不计模型成功。

## 2. 打开和演示

1. 双击项目根目录 `启动智能调度.cmd`，等待本地后端5000、前端8080就绪。使用原项目演示账号 `user1 / user1` 登录。
2. 打开 [智能实验中心](http://127.0.0.1:8080/#/intelligence)。在“实验前客流预测”选择基地、起始日与天数，查看预测和同期对照；点击填入，仍需核对并确认实验。
3. 在描述框输入“下周成都基地，客流涨两成，加一场雷暴”。当前默认用本地模型提取，缺漏时最多补提取一次；字段附原文依据。日期由日历解析器处理，生成和填入草稿都不会运行实验。内存不足或某条提取未通过时明确回退模板。
4. 核对表单中的日期、天数、天气、资源、航班数、起飞窗口和种子，点击“确认条件并运行”。
5. 查看分类命中率、逐航班预测/模拟实际分钟、均值基准、原恢复计划和五策略代价；可以导出CSV、同条件重跑、比较三种天气。点击“查看依据”查看参考条件变化对模型预测的影响。
6. 关闭“模型参与预测与推荐”，同条件再运行，模拟实际结果应保持一致；预测使用均值对照，恢复策略并列展示。
7. 在“模型复核与回退”先运行正常复核，再按确认弹窗运行失准演示。延误项会被停用；再运行正常复核可恢复。演示只扰动内存中的预测，不修改权重。
8. 在原“航班甘特图”中比较排班算法，点击选用，再点击原“一键排班”。原异常页先选事件并完成影响分析，再比较恢复建议；确认和执行仍使用原页面流程。
9. 用完双击 `停止智能调度.cmd`，按路径、进程身份和启动时间核对后，只停止本项目登记的服务树。

启动脚本仅使用现有 `.venv` 与 `demo/node_modules`，不会自动安装软件。服务只绑定127.0.0.1，日志在 `.artifacts/`。本轮没有使用SSH、付费推理、推送GitHub或公网部署。

## 3. 实现口径及限制

### 实验与延误预测

- 完整保存默认条件、日期、连续天数、客流比例、异常、分开的飞机/机组/登机口资源、种子和模型开关。同条件、同代码和同版本可复跑；最多2000架次，批量最多12组。
- 模拟实际分钟由天气、前序延误、异常、随机扰动及原跑道排队结果构造。延误定义为超过15分钟；标签及实际落地时间不作为输入特征。
- 机型按A319/A320/A321混合生成。训练与留出按场景隔离，留出基地与训练基地不同，客流、异常及起飞窗口范围更宽。
- `DictVectorizer` 加梯度提升分类/回归器离线拟合。模型版本保存条件清单、源码指纹和依赖版本。
- “查看依据”固定其他条件，把天气、前序状态、跑道容量等替换成可见参考值，再计算预测差。它解释模型行为，不是现实因果证明。

### 客流趋势

- 8个基地的日历史由原平台基准客流构造，含周季节、年季节、趋势和扰动，固定730天；明确标为模拟历史，不冒充航司真实数据。
- 另用真实历史 AirPassengers：1949—1960年国际航空月客流，共144个月，原单位千人，已换算人次。不能把该历史月数据填成当前中国机场的日客流。
- 使用固定版本的标准化与Ridge对数回归，输入历史滞后、日期与趋势；后28天日数据/后24个月月数据连续留出。多步预测只使用过去历史和此前预测，不偷看未来标签。同期对照为上周/上年同期。
- 日预测最多28天，页面填表最多7天；可支持历史结束后14天内开始的预测。超范围会明确报错。日比例以预测平均客流相对末周平均值计算，填入表单时遵守原0.5—2.0范围并提示。

### 排班建议

- 使用原项目三个算法；二分图选项在已筛选的完整往返链流程中映射原链覆盖服务。未筛选流程只并列展示，不用未经评估的路径自动推荐。
- 检查机型一致、航班不重复、60分钟周转、机场衔接、机队数量和基地闭合。违约计划不作为可执行候选；缺少完整机组执勤与法规检查，不声称生产可用。
- 教学代价为 `10000×未分配架次 + 100×使用飞机数 + 0.05×空闲分钟`。模型学习相对原默认计划的代价差；预测下限为候选已知未分配与飞机固定成本，避免少量航班场景估成零成本；候选已知计划代价更差时保留默认。
- 原默认算法本来就常常最优。必须同时报告默认命中率和实际成本差，不把小幅改善包装成大幅收益；该建议也不减少本次候选求解计算量。

### 恢复对照

- 不再用人为设置的五策略固定顺序作验收基准。对同一份航班、异常和资源调用原 RecoveryService，隔离副本上生成、确认、执行；飞机排除使用原链覆盖算法和相同默认机队配置，不改活动排班。
- 统一代价为 `延误分钟 + 240×取消或未恢复架次 + 8×资源变更次数`。页面分别显示真正取消与未恢复架次，240只是教学取消等价权重，不是人民币。
- 五策略直接调用原时间平移、资源替换、链重规划、航班合并、取消服务。附加检查在共同口径下执行，候选不可行不推荐。候选计划代价高于原可行方案时保留原方案；不读取未来标签作选择。
- 分别保存未保护的模型选项成本、保护后成本、原方案成本和事后最优参考值。恢复改善包含这项可见保护，不能全部归因于预测模型。
- 修复原时间偏移的跨月/跨年/闰日错误，以及原链覆盖机型不足时放宽机型的分支。原流程中未分配航班保留未分配状态，不能用错误机型填满。

### 周期复核

- 服务运行时每60秒查看是否到期，每7天检查固定权重；离线期间不运行，重启后补做过期检查。记录与停用状态绑定模型版本，重训不会继承旧版本误判。
- 当日固定种子生成新的30个异常场景与20个排班场景，日客流用历史末日之后28天的模拟新增数据。公开月数据没有新观测，不假装做了新增月数据复核。
- 不在线拟合或自动覆盖权重；手动重训是另一个显式操作。复核失败时只停用相应模块，保留均值/同期预测及原确定性调度路径。运行失败会保留错误记录。

### 本地语言模型

- 官方 Qwen2.5-1.5B-Instruct，固定修订与完整权重SHA-256验证。本机CPU、4线程、float32推理；没有微调或重新下载权重。原0.5B和失败评估保留。
- 模型先用中文摘录，独立规范化模块只读取模型输出。例如模型写“减少20%”，程序换成0.8；模型没提取航班数，程序不能把模板值算进模型成绩。中文字段名、单位、天气/事件枚举及空值会规范化，原始输出全部保存。
- 最多一次反馈，只列要补充或修正的中文字段名，不给期望值。保留已核对正确的首轮模型值，再合并第二轮模型补丁，避免重写时丢字段。`model_field_sources`逐字段记录来自首轮还是补丁；来源审计不从原文提取或补值。
- 最长500字；日期与天数由日历解析器处理，不计作模型提取。新协议在新留出运行前固定：8开发+16旧回归+24新留出，总体与新留出两轮合并正确率均≥90%，带回退草稿100%正确。所有失败例保留，不挑例、不把模板补值计入模型成功。
- 当前48条首轮29/48，两轮合并48/48，新留出24/24，因此默认使用带校验纠错的模型流程。未知表达仍可能失败，草稿始终需人工确认。改动提示、解析源码或计算格式后，哈希不匹配会先回退模板，需重新评估。
- 原先强制BF16省内存，但本机AVX2没有对应硬件加速。完整FP32试跑更快，正式48条中位8.32秒、最长26.81秒（包含冷加载的首例）；该结果只代表本机与这组描述。约16GB内存机器已验证，加载前需约7GB可用物理内存，不足直接回退模板。FP32内存占用更高，磁盘权重仍约3.09GB。参见[PyTorch CPU格式说明](https://pytorch.org/blog/empowering-pytorch-on-intel-xeon-scalable-processors-with-bfloat16/)。

## 5. 复核和复现

本机依赖已安装，本轮不需要重复安装。首次准备另一台电脑时：

```powershell
python -m venv .venv
.\.venv\Scripts\python.exe -m pip install -r backend/requirements-windows.lock.txt
cd demo
npm ci
cd ..
.\.venv\Scripts\python.exe -B scripts/download_pretrained.py
.\.venv\Scripts\python.exe -B scripts/install_pretrained.py
.\.venv\Scripts\python.exe -B scripts/download_language_model.py
```

首次恢复无需重训：下载器从固定GitHub Release获取约543KiB的小模型包，验证ZIP哈希后由安装器恢复。详见[交接说明](HANDOFF.md)。需要重新训练或复核公开数据时，`download_intelligence_assets.py --skip-model`只准备两个公开CSV；1.5B使用独立脚本。旧脚本不带该参数会额外准备0.5B。下载均核验固定哈希，不静默接受上游数据更换。可用 `AEROTOWER_CURL` 指定curl，本机非Schannel便携curl仅替代该调用；不要关闭TLS验证。

日常只检查语言可运行 `scripts/evaluate_language.py`；它保存完整48条记录并归档前一份结果。`--development-only`只测8条开发例，不发布成绩；同一版本可用`--resume`续跑连续进度。完成后运行 `scripts/audit_language_evaluation.py`，核对每个计入模型成功的字段确实来自模型输出。检查不会替你确认或运行实验。

回归与构建：

```powershell
$env:OMP_NUM_THREADS='4'
$env:AEROTOWER_DISABLE_MONITOR='1'
.\.venv\Scripts\python.exe -B -m unittest discover -s tests -p 'test_*.py' -v
cd demo
$env:NODE_OPTIONS='--openssl-legacy-provider'
npm run build
```

VueCLI4/Webpack4在Node24上需要上述仅当前进程的OpenSSL兼容参数。启动脚本已设置。浏览器检查使用本机已有Playwright和Chrome，路径通过 `AEROTOWER_PLAYWRIGHT_MODULE` 指定，再运行两个 `scripts/check_intelligence*.cjs`。未在同学电脑上实测，不保证免配置迁移。
